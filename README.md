# DWM

Lightweight Node.js rewrite of the legacy Laravel application.

The goal is feature parity without carrying Laravel/PHP runtime requirements into the final deployment.

## Why this architecture

DWM uses server-rendered EJS pages instead of a JavaScript SPA. This keeps initial page weight low and allows the application to remain usable on slow field connections.

The global frontend intentionally has:

- no React/Vue
- no Tailwind runtime
- no Bootstrap
- no icon font
- no third-party CDN requirement
- very small vanilla JavaScript
- one small custom CSS file

Heavy dependencies should only be introduced for the routes that need them.

## Runtime

- Node.js 22+
- MySQL/MariaDB
- Express
- EJS
- PM2
- Nginx

## Existing database

The foundation is designed to read the existing legacy tables, including `xusers`, `projects`, `wellinfo`, and the asset/PM/inspection tables.

Existing bcrypt password hashes generated by Laravel are supported. `$2y$` hashes are normalized for Node bcrypt compatibility during verification.

## Local/VPS setup

```bash
cp .env.example .env
nano .env
npm install
npm run db:check
npm start
```

Health endpoint:

```bash
curl http://127.0.0.1:3020/health
```

Production:

```bash
npm ci --omit=dev
pm2 start ecosystem.config.cjs
pm2 save
```

## Database import

If starting on a clean database:

```bash
chmod +x scripts/import-existing-sql.sh
./scripts/import-existing-sql.sh dwm /path/to/hrdynt_stepoil.sql
```

Then set:

```env
DB_DATABASE=dwm
```

## Security model

- MASTER and Supervisor may access all projects.
- Operator and Staff are limited to their assigned `id_project`.
- Project/report ownership must be checked server-side.
- Destructive operations will use POST/DELETE semantics, not GET.
- Existing Laravel session records are not reused.
- Production secrets belong only in `.env`.

## Migration rule

The production Laravel application should remain available until every item in `MIGRATION_STATUS.md` is implemented and regression-tested.
